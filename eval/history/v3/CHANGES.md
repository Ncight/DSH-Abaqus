# 指引第三版（v3）相对第二版（v2）的改动

依据：评测 `hard_base`（裸 DSH）和 `hard_live`（第二版）在难题组 8 道题上各两遍的全部运行记录，加上此前基础组的记录。
难题组上两种配置都是 16/16 通过，所以这一版不是由"做错的题"驱动的，而是由**步骤级的浪费**驱动的：把运行记录里每一次工具调用的耗时和报错原文统计出来，找出最大的几项。报错统计只用调优集的 48 次运行。

## 发现的问题

1. **第二版让模型在小模型上用多核求解，反而慢了好几倍**。AGENTS.md 的工具表写着"可加 `--cpus 4`"，模型于是几乎每次都加。本机实测（`eval/skill_checks/cpu_bench.py`）：并行作业启动要多花约 9 秒，每个增量步再多花 0.05～0.1 秒；100 个梁单元、1210 个增量步的作业 2 核 174 秒、1 核 30 秒；实体单元要到约 4 万个以上多核才划算（12 万单元：4 核 34 秒、1 核 57 秒）。难题组第二版的 16 次运行里，多核求解占了总耗时的 26%（2195 秒 / 8541 秒）。
2. **读结果库的脚本是报错最多的环节**。读 ODB 的脚本有 74 次调用以报错结束（经 `abq python` 的调用每 4 次有 1 次），其中 50 次集中在下面几类写法上：

   | 报错 | 次数 | 原因 |
   |---|---|---|
   | `'FieldOutput' object has no attribute 'position'` 等 | 13 | 臆造的属性名（position、components、valid） |
   | `Slice for an ODB Sequence is not supported` | 12 | 对 frames、values 做切片 |
   | `KeyError`（多为集合名） | 8 | 集合名大小写；直接写的 INP 的集合在实例上而不在装配上 |
   | `… is not JSON serializable` | 7 | ODB 取出的分量是 numpy.float32，没有先转成 float |
   | `'OdbMeshNodeArray' object has no attribute 'label'` 等 | 5 | 把节点数组当成单个节点 |
   | FieldValue、OdbFrame 等对象的臆造属性 | 5 | 同上 |

3. **第二版的后处理 skill 自己有两行错的示例**：`odb.steps['Modes'].frames[1:]`（切片，必然报错），以及写死的历程区域名 `'Assembly ASSEMBLY'`（直接写的 INP 里叫 `'Assembly Assembly-1'`）。这两行当时没有实跑验证。核对全部 skill 后，CDP、摩尔-库仑、Tie 的示例行也没有对应的实跑脚本（这次实跑确认内容是对的）。
4. **取"某个集合上的合计/平均"只能写脚本**。`abq odb` 只给全场最值和按坐标的探针；支座反力、荷载-位移曲线这类最常用的量都要自己写 ODB 脚本，平均每次运行 5～6 次 `abq python` 调用。
5. **理想化选得过重**。预应力拉索一题，四次运行里有一次（第二版）用实体单元去建一根直径 10 mm、长 10 m 的钢丝，在加载方式上反复试了八个变体，直到超时（之前按"先交付"规则交出的结果是对的，所以仍然通过）。
6. 工具输出的小问题：纯舍入误差的量被完整打印成几十位小数；带频率分析步的模型里，探针时程把振型帧也当成了时间历程；直接运行 skill 目录里的模板，作业文件会生成在 skill 目录里。

## 改动

| 改动 | 针对 | 是否经运行验证 |
|---|---|---|
| 工具：`abq run`/`abq sweep` 对少于 20000 个节点的模型自动用 1 核（`--force-cpus` 可强制）；AGENTS.md 的"可加 `--cpus 4`"改为"几万个单元以上再加" | 问题 1 | 同一作业经工具运行：`--cpus 4` 自动改 1 核，30.5 秒（第二版评测里同一模型 2 核 197 秒） |
| 后处理 skill 的"常用写法"整段重写：每一行与验证脚本 `eval/skill_checks/chk_odb_recipes.py` 逐字相同；新增按名字找集合的写法（装配级、实例级都能找到）和"会报错的写法 → 正确写法"对照表 | 问题 2、3 | 在 CAE 建的模型和直接写的 INP 两个结果库上逐行实跑；表里每个"会报错"的写法也实测确实报错 |
| 提示表新增 8 条（上表各类报错 + 脚本编码），`KeyError` 的提示补充 ODB 集合的位置 | 问题 2 | 每条正则用运行记录里的报错原文自测，互不误触发 |
| 工具：`abq odb --set 集合名`（合计/平均/范围，小集合逐节点列出）、`--series`（集合上的逐帧合计或平均）、`--sets`（列出集合） | 问题 4 | 两个结果库实跑；`summary.json` 的键路径有专门的验证脚本 |
| AGENTS.md 流程第 3 步：先定理想化（细长构件用梁/桁架、薄板用壳、轴对称用轴对称单元，块体才用实体）；关心的位置建成命名集合 | 问题 4、5 | 工作方法 |
| 工具：舍入误差量级的量显示为 0；探针/集合时程不再包含特征值分析步的帧；带 `--probe`/`--set` 时只输出该部分；时程表给出每列的全程极值；skill 目录里的模板自动复制到当前目录再运行 | 问题 6 | 实跑 |
| 新增 `eval/skill_checks/`：18 条验证链（建模 → 求解 → 读结果 → 与手算对比），覆盖全部 skill 的代码示例；`eval/skill_snippets.py` 核对 skill 里出现的每个接口名都被某个实跑过的脚本用到 | 问题 3 | 18 条全部通过；接口名核对 0 个遗漏 |

新验证的材料示例：CDP 单单元受拉（峰值应力、软化段应力、受拉损伤、刚度退化与手算一致）；摩尔-库仑无侧限抗压强度与 2c·cosφ/(1−sinφ) 一致；Tie（`master=`/`slave=`，位置容差）叠块压缩与理论一致。

## 局限

- 这一版的目标是减少无效的耗时和试错，不是提高通过率——难题组上两种配置本来就全部通过。
- 报错统计只用了调优集的运行记录；多核耗时的统计用了难题组全部 16 次运行（只统计耗时，不涉及题目内容）。保留集的失败记录没有用于改写指引。
- 接口名核对只证明接口存在并在跑通的脚本里用过，不保证 skill 里每个参数都对；逐字核对目前只覆盖后处理 skill。
- 多核阈值来自本机、Abaqus 2021、实体单元的测量；换机器或换版本后应重跑 `cpu_bench.py`。
